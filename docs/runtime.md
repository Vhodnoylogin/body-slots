# Independent slot runtime

`body_slots_runtime_api.h` is an additive copied-record API. Existing definition, configuration, instance and native14 layouts are unchanged. Body Slots computes slot placement, spherical containment, entry/exit/hover, binding availability, offers, slot reservations and its committed-content mirror. VRIK supplies poses. HIGGS supplies the hand state, input, grants and physical/inventory operation receipts. Native14 compatibility banks are separate and do not create instances.

The current bounds are 256 active logical instances, 256 saved runtime override keys (including dormant keys), 64 behavior registrations, 64 event subscriptions, 8 proposals per behavior, 512 recent offers and 64 pending/action-status records. One behavior owns the execution route for each instance. Registrations and subscriptions require existing live registry writer/observer tokens. Behavior, binding and visual writes require the instance owner's writer token; there is no provider-name impersonation or implicit cross-provider delegation.

## Frames and geometry

The internal game adapter supplies `UpdateRuntime(RuntimeFrame)` on a declared main update boundary: epoch, monotonically increasing frame/time, body generation, two explicitly identified physical-hand probes and copied resolved anchors keyed by instance handle. Missing or invalid anchors make their slots unavailable; missing/invalid hands produce exits and cannot produce actions. The runtime does not infer a hand occupancy classification. Uniform positive anchor scale affects local position, region center and radius. Rotations must be proper orthonormal matrices; reflected/nonfinite/degenerate transforms are rejected. Sphere boundary points are inside. Geometry observations do not depend on content occupancy, visibility, content reservation or physical-hand access policy.

Every slot has a default body-node binding using its effective authored anchor. `SetBinding` can supply an exact equipment node and a required worn equipment form, or gate a body-node binding by that worn form. The adapter resolves the exact node, checks worn equipment and uses a distinct anchor-generation cookie for model/node replacement. It supplies no substitute node when resolution fails. An unresolved saved equipment form uses explicit binding kind `UnresolvedEquipment`; the core keeps it unavailable even if an anchor is accidentally supplied. The equipment provider remains responsible for validating durable particular-item instance keys; a base form gate alone does not establish a bag's durable identity.

`CopyRuntime` returns copied configured geometry, bindings, content and presentation records, including unavailable slots and current containment. Clients subscribing after entry can inspect that snapshot. Events are synchronous on the thread that updates geometry or detects configuration invalidation; callbacks must consume copied observations or queue their work for the proper game phase. Configuration, save, body and anchor changes revoke old offers. Geometry alone does not cancel a provider operation after its execution callback has started; the slot reservation remains until its actual HIGGS/provider outcome.

## Action and receipt sequence

`CollectOffers` receives a coherent HIGGS input context and the matching virtual-hand probe sample. It copies both held-reference and equipped-form observations, their observation mask/occupancy, physical hand, button/edge and input sequence without classifying them. Providers inspect immutable slot/input contexts and return at most eight eligibility/action proposals. Offer callbacks must not mutate inventory. Entry, hover, presentation and a copied offer do not execute gameplay.

Overlapping offers sort by descending explicit priority, then instance handle, registration and action identifiers. The adapter submits them to HIGGS alongside other hand actions. Each behavior names its real provider-owned HIGGS client and executor; that executor must explicitly authorize the Body Slots recognizer through the negotiated HIGGS routing interface. A HIGGS executor notification for a Body Slots request only queues it. The safe main-phase adapter revalidates the winning grant and calls `DispatchSelected`, which invokes exactly that behavior's executor. The provider uses its own authorized HIGGS route for hand/inventory operations and reports HIGGS results under its own token.

Dispatch validates the exact cached offer, epoch, input sequence, physical hand, HIGGS request/grant and echoed offer/policy identifiers. It permits a later main frame only while current containment, configuration, content, body and anchor generations still match. The adapter separately checks current HIGGS hand/item and grant authority. Only one pending action reserves a slot. Once dispatch starts, failure does not select another action on the same input. Recent consumed inputs and offers have bounded history; HIGGS remains responsible for global input/grant deduplication. Old terminal status records are reclaimed when the 64-record pool needs space; process-local identifiers never repeat after save transitions.

`ReportContentCommit` only accepts the assigned instance owner with matching local request, epoch, HIGGS request/grant and expected content version. The installed internal `ContentCommitValidator` checks the matching HIGGS executor's current grant or confirmed operation result outside registry/runtime locks. Without that validator, receipts return `Unavailable`. The core revalidates live ownership, configuration and pending state after the hook. New content versions increment by exactly one; zero quantity requires zero content identity. Exact duplicate receipts are idempotent, stale receipts conflict and a committed mirror never rolls back. Completion/failure/cancellation remain distinct from content commitment. The game adapter polls HIGGS outcomes and calls `ApplyHandResult` to retire revoked, expired, failed or cancelled grants. Before updating geometry/configuration it also reports confirmed HIGGS `Committed`/`Completed` stages through that function. This marks irreversible hand commitment separately from the content mirror: later geometry loss preserves the pending provider receipt while the same instance/content scope exists. No content is inferred from that notification. An externally committed operation awaits its provider receipt even if subsequent hand completion fails. `CopyActionStatus` and internal `CopyActionProgress` expose bounded copied progress. Body Slots never performs inventory mutation.

Callbacks run outside both service mutexes and may reenter copied queries and commit reporting. External removal deactivates a registration and drains calls before returning. Every draining removal or client release attempted from any runtime callback returns `Conflict` without removing anything; retry after the callback returns. This prevents self-removal and cross-callback deadlocks. Base `ReleaseClient` marks the lease as releasing, invokes the optional runtime drain hook outside the registry mutex, then removes registry ownership. Registration and callback invocation revalidate the live owner. A save generation change retires behavior bindings to old handles; event observers survive. Retired in-flight registrations count against the 64 limit until drained. A removed/retired handle returning `NotFound` has no future runtime calls; callers must still synchronize their own concurrent registration/removal attempts.

## Saved overrides and presentation

`SetBinding` and `SetVisual` persist stable `InstanceCustomizationKey` overrides: instance owner, equipment key, slot key and definition provider/key. Registry state owns these records under its existing mutex. Removing an instance/provider makes the overrides dormant rather than deleting them. `CopySavedCustomizations` exposes dormant records and `ClearSavedCustomization` removes selected fields using exact nonzero save/view expectations and owner authorization. Existing configuration APIs continue to own saved position, rotation, radius, region center and enabled state.

The bounded portable `BSRT` v1 codec stores 816-byte records, separately from BSCF definition geometry and BSCI instance geometry. It contains only binding/node/form and holder/preview asset settings plus stable keys; runtime handles, grants, activation, callback pointers, content assignments, content versions and readiness are not serialized. All three chunks are decoded/validated before one registry publication through the extended `LoadConfigurationBatch`. Malformed or duplicate records leave all three stores unchanged. Absent BSRT clears runtime overrides on load, preserving compatibility with earlier saves. Saving copies the three stores under the same registry lock before encoding. The plugin must run `RemapRuntimeCustomizationForms` with SKSE form resolution before loading BSRT; unresolved forms make only the affected binding dormant. Decode/remap failures do not alter caller output. `ResetSaveScope` clears all three saved stores.

Holder ownership, relative mesh paths, requested preview content version, visual revision and copied ready/failed state are separate from interaction availability. `ReportPresentation` accepts only matching visual/content revisions. An empty visual specification has state `None`. A preview represents existing provider content and creates no stock. The adapter owns actual scene nodes and asset load results; saved settings do not assert successful rendering.

## Current limits

This runtime uses the existing spherical access geometry. Capsules/boxes, multiple probes per slot, shared behavior bindings, standalone zone authoring conveniences, drag recognition/gesture UI and native14 assignment migration are not implemented by this API. A program can create ordinary independently observable zones through the existing definition and instance APIs. Saved geometry edits already use their revision-checked configuration APIs; no new drag input implementation is implied. Equipment identity semantics, asset suitability, reachability and the exact game pose/phase adapter require game qualification. The production core tests exercise geometry, overlapping offers, stale/duplicate/failed actions, authority validation, reentrant callbacks, draining release, dormant saved overrides, form remapping and atomic three-chunk load rejection without claiming headset validation.
