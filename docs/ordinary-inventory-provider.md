# Ordinary items through the shared inventory executor

The compilable SDK helper in [`examples/ordinary_inventory_provider.h`](../examples/ordinary_inventory_provider.h) and its implementation compose the existing public Body Slots and HIGGS tables. It is not part of the Body Slots DLL or a new ABI. A mod owns one instance, its selection/acceptance policy and its content mirror. The helper supplies the asynchronous protocol for ordinary player-inventory withdrawal into an actual HIGGS grip and storage of an actual HIGGS-held item into player inventory. It contains no Skyrim/CommonLib calls, `RemoveItem`, object spawning, pickup implementation or replacement grab mechanic.

## Consumer responsibilities

Negotiate the public Runtime, Behavior and Game tables from Body Slots and the Hand, Routing, Inventory and Transactions tables from HIGGS. Supply a live Body Slots writer and instance, a dedicated HIGGS client, and a read-only thread-safe policy callback. The callback receives an immutable `SourceActionContext` and returns an `OrdinaryItemPlan`: the transfer direction, base form/stack ordinal/quantity for a withdrawal, and the content identity/count to mirror after successful completion. Returning false produces no offer. Base forms, accepted item semantics and the relationship between player inventory and the slot's logical content belong to this policy; the helper does not invent stock or assign game-equipment semantics.

Inventory capability bits are zero before HIGGS installs its native backend. The game connection must also be ready. Retry negotiation/attachment after native maintenance rather than treating an early table as a permanently available executor. Keep policy data and the helper alive until callback drainage completes. `Attach`, `Tick`, `Cancel` and `Detach` belong to one serialized owner thread; only the registered copied-context callbacks may arrive concurrently. Tick runs in the consumer's safe main update after HIGGS native maintenance, never in a controller callback.

The policy receives both item sources. Storage requires the known, allowed HIGGS-held reference; a game-equipped weapon alone is never accepted as a held object. A simultaneous equipped weapon does not hide a held potion. Withdrawal requires an explicitly known empty physical hand. The helper preserves the selected plan in a bounded offer cache; it does not silently choose a different stack after selection fails. Its original HIGGS action request ID is also its transfer idempotency key, so the supplied client must reserve that key convention for this helper.

## Authority and receipts

Attachment registers a generic HIGGS action executor, explicitly authorizes the Body Slots recognizer and registers a source-aware Body Slots behavior. The controller-thread notification only records the selected action identity. Body Slots's actual safe-phase dispatch queues the operation. These steps do not mutate inventory.

For a withdrawal, Tick queues a native selection ticket and waits for `READY`, preserving the exact selected native identity. For storage it copies the complete public native held identity when building the offer, validates it against that copied context and retains it with the selected plan. Before transfer admission it requires that exact instance, generation and identity metadata again; an equal reference/base form cannot substitute a replacement instance. The coordinator independently rechecks the same identity at transaction admission. It obtains the separate typed transaction executor through `Inventory.GetExecutor` under the same consumer client and submits a transfer borrowing the selected action's grant. The generic action executor and native transfer executor are different tokens. The helper never calls `BeginMutation` or fabricates a transfer receipt: the shared native executor and transaction coordinator own those steps, including independent physical release/grip confirmation.

An accepted transfer or successful inventory removal is not a successful withdrawal into a hand. While the coordinator waits for actual grip, the helper forwards confirmed irreversible evidence to its original HIGGS action but leaves the Body Slots content mirror unchanged. Only a successfully completed transfer with the matching disposition and physical confirmation commits that mirror. It then completes the original action, reports the matching Body Slots completion, releases the selection ticket and releases the original grant. Mirror failure does not trigger a fresh transfer or invented compensation.

Cancellation, compensated withdrawal and uncertain mutation remain different outcomes. A failed/compensated operation does not publish the planned content change. `RecoveryRequired` retains the actual transfer record and operation IDs, blocks new offers and prevents normal detachment. It is not an automatic retry instruction. A real native reconciliation remains an explicit owner operation; observing its confirmed result can resume final reporting. If an instance/save disappears, no old receipt is projected into a recreated handle or another epoch. During full provider shutdown, the owner can separately drain/release both supplied client leases before destroying the helper; that ends callbacks/authority and does not undo or reconcile an uncertain inventory mutation.

## Limits and checks

The helper handles one outstanding operation for one instance. It supplies no UI, assignment persistence, whole-inventory browser, arbitrary container semantics, proxy generation or game-equipment handler. Consumer projection remains responsible for the meaning of the slot's content identity and quantity. An unavailable anchor can preserve a started operation; removal/recreation or a save change is a different scope and may require explicit recovery.

Run `python tests/run_inventory_provider_tests.py --higgs-root <cooperation-fork> --build-dir <external-directory>`. The SDK is compiled separately as C++17 with warnings as errors. The protocol executable uses actual Body Slots services, actual public HIGGS tables and actual inventory/transaction coordinators; only native engine operations, physical observations and pose integration are synthetic. CMake additionally builds `body_slots_ordinary_inventory_provider` and `body_slots_inventory_provider_tests`. These checks demonstrate protocol composition, not an installed potion mod or in-game qualification.
