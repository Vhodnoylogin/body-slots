# Ordinary items through the shared inventory executor

Accepted deferred work is validated against its own source. Changes to other slots, their content or their anchors do not cancel an armed draw. A change or loss of the original source, body, anchor or hand observation invalidates it permanently; restoration requires a new press. Presentation-only changes preserve geometry and do not synthesize exit/entry events. Before admission, offers still use the global invalidation fence.

A completed transfer and following its original grip are separate outcomes. If the original press or possession is already stale, the helper records `InventoryProviderProgress.releaseStatus` and still settles the factual transfer; it never invents a replacement press or repeats delivery. Other continuation errors retain recovery handling. HIGGS preserves exact child receipts across natural grant expiry without renewing permission to mutate. Cancellation before factual completion remains subject to the existing recovery/compensation contract. These additions are source-reviewed and compiled only, with no tests or gameplay qualification.

The compilable SDK helper in [`examples/ordinary_inventory_provider.h`](../examples/ordinary_inventory_provider.h) and its implementation compose the existing public VR Interaction Framework and HIGGS tables. It is not part of the VR Interaction Framework DLL or a new ABI. A mod owns one instance, its selection/acceptance policy and its content mirror. The helper supplies the asynchronous protocol for ordinary player-inventory withdrawal into an actual HIGGS grip and storage of an actual HIGGS-held item into player inventory. It contains no Skyrim/CommonLib calls, `RemoveItem`, object spawning, pickup implementation or replacement grab mechanic.

### Save scope, terminal receipts and cleanup

Attachment verifies the source instance in a coherent runtime copy and captures its nonzero logical save generation. Queueing must still match that generation. The progress record exposes this accepted `saveGeneration`, separately from the receipt's physical HIGGS epoch. Moving between cell physics worlds can change that epoch without loading another save.

A positively observed save-generation or HIGGS-epoch transition marks `sourceRetired` and cancels unstarted work. A missing handle, unavailable provider or failed read alone never authorizes this cleanup. Work with no admitted transfer can release its selection and grant without reporting into a vanished runtime source. Started transfers still require an exact terminal factual result; unresolved uncertainty stays in recovery. Retired sources receive no content mirror or old-grip continuation. A consumer may retain its own logical assignment from factual storage only after freshly verifying that the operation's captured save generation still matches its current save.

Exact terminal completed/cancelled/rejected receipt copies are immutable and reused during final reporting or cleanup retries. Nonterminal and unresolved recovery receipts are always observed again. This permits cleanup after an epoch reset has retired provider history without inventing success or replaying inventory work. HIGGS additionally retains the correlated parent, child action and actual transaction through terminal reporting until the consumer acknowledges consumption with `ReleaseGrant`; reporting `COMPLETED` alone is not that acknowledgement. Removing only a spatial recognizer does not acknowledge another consumer's result.

`saveGeneration` and `sourceRetired` are source-level SDK helper fields, not additions to an exported binary table. These lifecycle changes have not been tested. Compilation, where separately recorded, does not establish loading, cancellation or save behavior in Skyrim.

### Fresh source admission

The opt-in held-release/deferred-exit paths negotiate `GameApi3::CopyFrameObservation`. It copies the adapter's actual spatial frame ID, epoch and observation-start timestamp in steady-clock nanoseconds. The timestamp is captured before reading hands/anchors and is not renewed after presentation or by a query. A delayed or frozen first frame therefore cannot acquire a new freshness window merely because this consumer first saw it now. The old GameApi1/2 layouts and query versions remain exact.

Immediately before either enhanced storage or withdrawal admission, the helper uses the existing HIGGS `AuthorizedDispatch2.Invoke` fence. It verifies the still-valid accepted source and matches that source to a Framework observation and a native hand snapshot no older than100ms. A deferred withdrawal additionally requires the original held press and a valid exit. Storage rechecks source availability/content/body/anchor but does not require the hand to remain inside after its already eligible release. It does not turn hand motion into a second activation condition. These services permit admission only; they do not renew authority or erase a started transfer's factual result.

## Consumer responsibilities

Negotiate the public Runtime, Behavior and Game tables from VR Interaction Framework and the Hand, Routing, Inventory and Transactions tables from HIGGS. Supply a live VR Interaction Framework writer and instance, a dedicated HIGGS client, and a read-only thread-safe policy callback. The callback receives an immutable `SourceActionContext` and returns an `OrdinaryItemPlan`: the transfer direction, base form/stack ordinal/quantity for a withdrawal, and the content identity/count to mirror after successful completion. Returning false produces no offer. Base forms, accepted item semantics and the relationship between player inventory and the slot's logical content belong to this policy; the helper does not invent stock or assign game-equipment semantics.

Inventory capability bits are zero before HIGGS installs its native backend. The game connection must also be ready. Retry negotiation/attachment after native maintenance rather than treating an early table as a permanently available executor. Keep policy data and the helper alive until callback drainage completes. `Attach`, `Tick`, `Cancel` and `Detach` belong to one serialized owner thread; only the registered copied-context callbacks may arrive concurrently. Tick runs in the consumer's safe main update after HIGGS native maintenance, never in a controller callback.

`InventoryProviderConfig::storeEdge` defaults to `HIGGS_INPUT_DOWN`, preserving existing consumers. A provider may set it to `HIGGS_INPUT_UP` to offer storage on a fresh release while an item is still HIGGS-held. These are the only accepted values; withdrawal always requires Down. The policy still chooses eligible button/context combinations and must return false when no action applies. If no storage action is selected, the unconsumed Up remains available to the native release path. This setting changes only SDK helper source behavior; public VR Interaction Framework/HIGGS table layouts are unchanged.

An Up belonging to an earlier consumed Down cannot be consumed as another action, even after that Down's executor released its grant. `storeEdge=Up` alone therefore does not reproduce a pouch's complete draw-and-return gesture. The semantic release option below supplies a separate HIGGS-generated intent instead of reusing that Up.

### Release into a bag and draw by pulling out

The opt-in `storeOnHeldRelease` uses HIGGS's new `HeldRelease` service. Set `InventoryProviderTables::behaviorOptions` to the separately negotiated `BehaviorApi2` table, `gameServices` to `GameApi2`, and `releases` to HIGGS's `HIGGS_HeldReleaseInterface`. The old v1 table pointers remain separately negotiated. Attachment refuses missing services; it does not substitute a trigger or a second raw-input hook. `GameApi2::CopyInputServices` reports whether the Framework adapter actually subscribed to HIGGS's held-release recognizer.

The provider policy receives `HIGGS_INPUT_HELD_RELEASE` (edge3) with the physical button and a new semantic intent ID while the item is still held. This is a pre-drop action opportunity, not the hardware `Up` and not its original `Down`. HIGGS owns correlation with native possession and the consumed press. The Framework geometry and source filters select the bag; the provider decides whether the actual item fits. Its proposal competes with native mouth/stash and other hand uses in HIGGS's existing shared admission window. Only behaviors explicitly registered with `kBehaviorHeldReleaseInput` receive this new edge. Existing v1 behaviors retain their previous input domain.

Set `withdrawOnExit` to arm a withdrawal on `Down` inside the slot. The helper retains the original plan and pins a read-only native selection ticket, but requests no physical or inventory transfer while the hand remains inside. The same still-held original sequence must exit an available, unchanged source. `kBehaviorDeferredExit` permits initial empty-hand dispatch when a fast pull has already crossed the boundary between Down and admission; source validation and the held-sequence check still precede transfer. Releasing/cancelling before exit, losing tracking, replacing/removing the bag or body, changing save/configuration/content, a stale frame or expiring authority cancels the unstarted draw. An invalid source producing an apparent `Exit` is never a valid draw. The selection remains exact; it is not retried against a different stack. The optional behavior table supplies a bounded 60-second grant; old registrations still use two seconds. `WaitingForExit` is observable helper progress, not an inventory receipt.

After an attested completed withdrawal with actual native grip, either new mode calls `HeldRelease.FollowInventoryGrip` before finishing the original action. HIGGS validates the actual transfer and associates that delivered item with its original press. The corresponding release can then drop the item normally outside all accepting zones, or offer its return inside a bag, without regrabbing or converting a consumed hardware Up into fresh input. Old helper consumers do not opt into this continuation automatically.

`withdrawOnExit` also requires `InventoryProviderTables::dispatch`, negotiated as HIGGS AuthorizedDispatch2. Once the native selection is ready and a valid exit has been observed, the helper invokes that existing fence once. Its synchronous callback rechecks the still-held original sequence and current deferred source, then admits the child transfer while controller input remains serialized. A release between the earlier observation and admission therefore cancels the unstarted draw. Waiting for exit or selection does not consume the single-use invocation; a refused invocation is cancelled instead of replayed.

These additions are source implementation under the owner's explicit no-testing instruction. The prior protocol checks described below do not establish the new semantic-release or pull-out behavior. No gameplay result is claimed.

The policy receives both item sources. Storage requires the known, allowed HIGGS-held reference; a game-equipped weapon alone is never accepted as a held object. A simultaneous equipped weapon does not hide a held potion. Withdrawal requires an explicitly known empty physical hand. The helper preserves the selected plan in a bounded offer cache; it does not silently choose a different stack after selection fails. Its original HIGGS action request ID is also its transfer idempotency key, so the supplied client must reserve that key convention for this helper.

## Authority and receipts

Attachment registers a generic HIGGS action executor, explicitly authorizes the VR Interaction Framework recognizer and registers a source-aware VR Interaction Framework behavior. The controller-thread notification only records the selected action identity. VR Interaction Framework's actual safe-phase dispatch queues the operation. These steps do not mutate inventory.

For a withdrawal, Tick queues a native selection ticket and waits for `READY`, preserving the exact selected native identity. For storage it copies the complete public native held identity when building the offer, validates it against that copied context and retains it with the selected plan. Before transfer admission it requires that exact instance, generation and identity metadata again; an equal reference/base form cannot substitute a replacement instance. The coordinator independently rechecks the same identity at transaction admission. It obtains the separate typed transaction executor through `Inventory.GetExecutor` under the same consumer client and submits a transfer borrowing the selected action's grant. The generic action executor and native transfer executor are different tokens. The helper never calls `BeginMutation` or fabricates a transfer receipt: the shared native executor and transaction coordinator own those steps, including independent physical release/grip confirmation.

An accepted transfer or successful inventory removal is not a successful withdrawal into a hand. While the coordinator waits for actual grip, the helper forwards confirmed irreversible evidence to its original HIGGS action but leaves the VR Interaction Framework content mirror unchanged. Only a successfully completed transfer with the matching disposition and physical confirmation commits that mirror. It then completes the original action, reports the matching VR Interaction Framework completion, releases the selection ticket and releases the original grant. Mirror failure does not trigger a fresh transfer or invented compensation.

Cancellation, compensated withdrawal and uncertain mutation remain different outcomes. A failed/compensated operation does not publish the planned content change. `RecoveryRequired` retains the actual transfer record and operation IDs, blocks new offers and prevents normal detachment. It is not an automatic retry instruction. A real native reconciliation remains an explicit owner operation; observing its confirmed result can resume final reporting. If an instance/save disappears, no old receipt is projected into a recreated handle or another epoch. During full provider shutdown, the owner can separately drain/release both supplied client leases before destroying the helper; that ends callbacks/authority and does not undo or reconcile an uncertain inventory mutation.

## Limits and checks

The helper handles one outstanding operation for one instance. It supplies no UI, assignment persistence, whole-inventory browser, arbitrary container semantics, proxy generation or game-equipment handler. Consumer projection remains responsible for the meaning of the slot's content identity and quantity. An unavailable anchor can preserve a started operation; removal/recreation or a save change is a different scope and may require explicit recovery.

Run `python tests/run_inventory_provider_tests.py --higgs-root <cooperation-fork> --build-dir <external-directory>`. The SDK is compiled separately as C++17 with warnings as errors. The protocol executable uses actual VR Interaction Framework services, actual public HIGGS tables and actual inventory/transaction coordinators; only native engine operations, physical observations and pose integration are synthetic. CMake additionally builds `body_slots_ordinary_inventory_provider` and `body_slots_inventory_provider_tests`. These checks demonstrate protocol composition, not an installed potion mod or in-game qualification.

The composition scenario also opens a HIGGS UI context during selection and after confirmed inventory removal but before actual grip. The former performs no withdrawal; the latter must obtain confirmed compensation. Neither changes the slot's content mirror, duplicates a potion or resumes the old action on returning to gameplay. This tests a real consumer protocol boundary rather than assuming a menu check inside the slot callback is sufficient.

Release-storage cases use the real input broker and helper with both physical hands: an unconsumed Down followed by Up stores the exact held identity, while a replaced instance or changed identity metadata refuses admission. They also cover an unselected Up returning unconsumed, an empty-hand Up producing no withdrawal, rejection of the Up owned by a completed withdrawal Down, and successful storage through a later fresh native input sequence. Native controller edge-history and in-game release behavior remain outside the synthetic physical adapter's qualification.
